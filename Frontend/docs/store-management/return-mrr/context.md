## Concept
Per-product partial (or full) reversal of an already-received MRR (`MaterialReceipt`), and **an MRR can be returned against multiple times** — e.g. more defects surface later, or the first return only covered some products. Each save creates its own permanent `MrrReturn` + `MrrReturnItem` audit row (independent of the live, event-log-style `material_receipt_items` table); the cap per product on any given return is **received minus everything already returned across all prior `MrrReturn`s for that receipt** (`remaining_quantity`), not just received. `is_returned`/`returned_at`/`returned_by` on `MaterialReceipt` are stamped as an informational "has been returned from at least once" marker only — they no longer gate anything (neither further returns nor `receiveSingleItem()`, see below).

## Backend
- **`MaterialReceiptController::receiveSingleItem()`'s `is_returned` guard was removed** (temporarily, "don't give this for now") — receiving is allowed again on a receipt after it's been returned against; only `status IN (CANCELLED, COMPLETED)` still blocks it.
- `App\Http\Controllers\Store\MrrReturnController::store()` — validates `material_receipt_id`, `return_date`/`return_type`/`reason`/`remarks` (all optional), and `items[].{product_id,return_quantity,remark}` (at least one `return_quantity > 0` required); rejects only if `status === 'CANCELLED'` (the old "already returned" block is gone — repeat returns are the point now). Before opening the transaction: dedups `MaterialReceiptItem` rows per product (latest/highest-id row per `product_id`, since `syncReceiptItems()` appends a new row per receiving event rather than updating in place — same pattern as `generatePdf()`); separately sums `MrrReturnItem.returned_quantity` grouped by `product_id` across **every** prior `MrrReturn` for this receipt (`MrrReturnItem::whereIn('mrr_return_id', MrrReturn::where('material_receipt_id', ...)->pluck('id'))`); computes `remaining = max(0, received - alreadyReturned)` per product and **hard-rejects** (`ValidationException`, no silent clamping) if any submitted `return_quantity` exceeds that product's `remaining`. Inside a `DB::transaction` with row locks: decrements `current_stock` per returned product (an inner `min()` against `remaining` is kept only as a defensive belt-and-suspenders against races between the pre-check and the lock, not as the primary guard), creates a `StockAdjustment` (`condition: 'DECREASED'`, `reason: 'MATERIAL_RECEIPT_RETURN'`), creates an `MrrReturnItem`, then sets `MrrReturn.custom_id = sprintf('MRR-RTN-%05d', $id)` and marks the source `MaterialReceipt`'s `is_returned/returned_at/returned_by` (informational only, see Concept above).
- `MaterialReceipt::mrrReturns()` — new `hasMany(MrrReturn::class)` + `#[LodataRelationship]`, needed so the frontend can expand `MaterialReceipts?...&$expand=...,mrrReturns($expand=items)` to compute remaining-returnable quantity client-side for the MRR picker.
- `MrrReturnController::nextCustomId()` — preview-only (`GET store/mrr-returns/next-custom-id`), returns `sprintf('MRR-RTN-%05d', MrrReturn::withTrashed()->max('id') + 1)`. Not reserved/locked — just the id the *next* save would get under normal single-writer use; used to populate the New Return dialog's Return No tile before the record exists.
- `MrrReturnController::generatePdf()` — `POST store/mrr-returns/{mrrReturn}/pdf`, renders `resources/views/pdf-templates/mrr-return.blade.php` (same DomPDF/Barryvdh pattern + letterhead style as `MaterialReceiptController::generatePdf()`). Items table columns: Item Code, Item Name, UOM, MRR Received Qty, Required Qty (from the PO line, matched via the latest `receiptItems` row's `po_item_id` per product — same dedup as elsewhere), Current Qty (`item.current_stock`, live), Return Qty, **Remark** (per-item, `mrr_return_items.remark`). The header Reference box shows the return-level Return Type/Reason only — no duplicate remarks block, since remarks are per-item now.
- `mrr_returns.return_type` / `.reason` — added via `2026_08_24_150000_add_return_type_and_reason_to_mrr_returns_table.php` (the `create_mrr_returns_table` migration had already run in this environment, so these landed as a separate add-column migration rather than editing the original). Free-form `string`, values are option-list codes (`QC_REJECTION`, `DAMAGED_MATERIAL`, etc. — see frontend `returnTypeOptions`/`reasonOptions`), not enums at the DB level.
- `MrrReturnController::summary()` — `total_returns`, `total_quantity`, `latest_return_date`, `returns_this_month`, `average_quantity_per_return`, `pending_returnable_mrrs` (now just `status != 'CANCELLED'` count — `is_returned` dropped from this filter since it's no longer a real eligibility gate; a receipt already fully returned would still count here even though it has nothing left to return, since checking that precisely would need summing all `MrrReturnItem`s per product across all receipts, not done for this metric).
- Routes: `POST store/mrr-returns`, `GET store/mrr-returns/summary`, `GET store/mrr-returns/next-custom-id`, `POST store/mrr-returns/{mrrReturn}/pdf`.
- Models `App\Models\Store\MrrReturn` (hasMany `items`, belongsTo `materialReceipt`/`returnedBy`) and `App\Models\Store\MrrReturnItem` (belongsTo `mrrReturn`/`item`) — both `guarded = []`, no `HasCustomId` trait (custom_id built manually since no `id_generator_settings` row exists for this entity). `#[LodataRelationship]` on relations → auto-exposed as `/odata/MrrReturns`. **Must also be explicitly registered** via `Lodata::discover(MrrReturn::class)`/`Lodata::discover(MrrReturnItem::class)` in `AppServiceProvider` (this app does NOT auto-discover Lodata entity sets — every model needs an explicit `discover()` call; omitting it 404s the OData endpoint even with the attributes in place).
- Tables: `mrr_returns` (custom_id, material_receipt_id FK, returned_by FK nullable, return_date, total_quantity, return_type, reason, remarks, soft-deletes), `mrr_return_items` (mrr_return_id FK, product_id FK, returned_quantity, rejected_quantity, remark — per-item, added via `2026_08_24_160000_add_remark_to_mrr_return_items_table.php`; distinct from `mrr_returns.remarks`, which is a single return-level note).

## Frontend (`ReturnMrrComponent`)
Single component, no separate form component.

- **Summary cards** (6, top row, `grid-cols-2 md:grid-cols-3 xl:grid-cols-6`): Total Returns, Total Quantity Returned, Returns This Month, Avg Qty / Return, Latest Return Date, Returnable MRRs (count of non-`CANCELLED` `MaterialReceipt` rows — see `pending_returnable_mrrs` note above, not precise per-product). Backed by `loadSummary()` → `GET store/mrr-returns/summary`.
- **List grid**: OData `MrrReturns`, expand `materialReceipt.supplier,returnedBy`. Columns: Return No, MRR No, Supplier, Return Date, Total Quantity, Returned By. "New" toolbar button → `openNewReturnDialog()`. Row actions: info-only (`showEditButton=false`, `showDeleteButton=false`, `showInfoButton=true`) — audit records are immutable, no edit/delete — plus one `customActionButtons` entry (`returnActionButtons`, icon `pdf-attachment`) wired to `downloadReturnPdf(row)`, which POSTs `store/mrr-returns/{id}/pdf` as a blob and opens it in a new tab (same pattern as `LocalMaterialReceiptComponent.openPdf()`). The info button → `viewReturn(row)` (see "Single shared dialog" below) — **there is no separate View dialog/template anymore**.

### Single shared dialog — "New Return" and "Return Details" are the SAME `ui5-dialog`
Per explicit instruction ("during info button click would appear same dialog as during create"), the info button no longer opens a distinct read-only view dialog with its own tile+grid layout. Instead there is exactly one `ui5-dialog` in the template, driven by `dialogMode: 'create' | 'view'` (`isViewMode` getter). `openNewReturnDialog()` sets `dialogMode = 'create'`; `viewReturn(row)` sets `dialogMode = 'view'`, fetches `GET MrrReturns({id})?$expand=materialReceipt($expand=supplier,purchaseOrder($expand=poItems),receiptItems($expand=item($expand=uom))),returnedBy,items($expand=item($expand=uom))` (`VIEW_EXPAND` constant) and populates the exact same fields `selectMrr()`/`completeReturn()` use in create mode (`selectedMrr`, `returnDate`, `returnType`, `reason`, `remarks`, `returnItems`) — so every section of the dialog renders identically in both modes, just with editable controls swapped for readonly ones and the footer's Complete Return button hidden.

Dialog (`w-[1000px] max-w-[95vw]`, `state="Information"`, plain `relative w-full h-full` wrapper + custom spinner overlay driven by `submitting || dialogLoading`, no `ui5-busy-indicator`/`ui5-card`), header text `isViewMode ? 'Return Details' : 'New Return'`, `border-t`/`ui5-title level="H6"` divided sections:
  1. **MRR combobox** — `*ngIf="!isViewMode"` only (view mode has no MRR to pick, it's already fixed). `getMrrOptions()` — `MaterialReceipts` filtered `status ne 'CANCELLED'` — `is_returned` dropped from the filter, a receipt stays selectable for further returns after already being returned against — expanded `supplier,department,requestBy,purchaseOrder($expand=poItems),receiptItems($expand=item($expand=uom)),mrrReturns($expand=items)` (`MRR_EXPAND` constant), auto-selects the first result on open when nothing is selected yet.
  2. **"Return Details" section** — a 4-field readonly-`ui5-input` row in both modes (**Return No** — create mode: live preview from `loadNextReturnNo()` → `GET store/mrr-returns/next-custom-id`; view mode: the record's actual saved `custom_id`; MRR No; Supplier; Original PO from `selectedMrr.purchaseOrder.custom_id`). Below that, **Return Date/Type/Reason** render as two mutually-exclusive `*ngIf` blocks on the SAME 3-field grid: create mode shows the editable `ui5-date-picker` (`onReturnDateChange(event)` — a typed TS method, NOT inline `$event.detail...` in the template, since Angular's strict template compiler (NG9) rejects `.detail` access directly on the native `Event` type) and `ui5-select` dropdowns (`onReturnTypeChange`/`onReasonChange`, same any-typed-handler reasoning — option `value` is the code, e.g. `QC_REJECTION`); view mode shows plain readonly `ui5-input`s with `returnDate` as-is and `getReturnTypeLabel(returnType)`/`getReasonLabel(reason)` for the human-readable label.
  3. **"Items to Return" section** — **not an ag-grid table**, a two-panel picker (idea borrowed from `LocalMaterialReceiptComponent`'s left product-progress panel, `Frontend/src/app/modules/store-management/local-material-receipt/local-material-receipt.component.html`): a `grid-cols-[280px_1fr]` layout, fixed `h-[320px]`, identical in both modes.
     - **Left panel** — searchable (`itemSearchTerm`/`onItemSearchInput()`/`filteredReturnItems` getter, matches on `item_code`/`product_name`) scrollable list of clickable product cards (`selectReturnItem(item)`), styled like `local-material-receipt`'s product cards (selected = `sapList_SelectionBackgroundColor` background + `sapSelectedColor` border/text, unselected = plain tile). Each card shows `{{ return_quantity }}/{{ received_quantity }}` and a `ui5-progress-indicator` (`itemProgressPercent(item)` — `return_quantity / received_quantity * 100`, `valueState="Positive"` once full). In view mode `return_quantity === received_quantity` is NOT generally true (a prior partial return leaves `received_quantity` unchanged) — the card there just reflects that return's actual saved `returned_quantity` against the product's total received.
     - **Right panel** — detail for `selectedReturnItem` (auto-set to the first return item whenever `returnItems` is (re)built): header is product name (bold), then a row with the `item_code · uom` subline plus a highlighted `ui5-badge` ("Returned: {{ already_returned_quantity }}", `color-scheme="8"`) — **number only, no progress-indicator bar here** (one was added then explicitly removed — don't re-add without a fresh instruction; `itemProgressPercent()` still exists and is still used, just by the left-panel cards, not this header). Then a 4-field readonly-`ui5-input` row (Required Qty, Received Qty, Current Qty, Rejected Qty), a `ui5-step-input` bound to `return_quantity` (`min:0`, **`max:remaining_quantity`** — received minus already-returned, per explicit instruction "Return Qty in form increase would based on received and returned qty"; this superseded an earlier explicit instruction that had it capped at `received_quantity` — the two conflicted and this is the one currently in force; `[disabled]="isViewMode"`, `onSelectedReturnQtyChange()` clamps against `remaining_quantity` and mutates the item object directly — same object reference as in `returnItems`, no separate data-sync step needed; its `valueStateMessage` shows both `received_quantity` and `already_returned_quantity` for context), and a plain `ui5-input` for the per-item **Remark** (`[readonly]="isViewMode"`). Empty-state message when nothing is selected.
     - `already_returned_quantity` — the historical amount already returned for that product **before** this draft (create mode: `alreadyReturnedByProduct` sum across prior `MrrReturn`s; view mode: that record's own saved `returned_quantity`, since a view is inherently "after the fact"). The left-panel cards' `itemProgressPercent(item)` bar is driven by `already_returned_quantity / received_quantity` — a historical "how much of what was received has already gone back" gauge, deliberately NOT based on the live/draft `return_quantity` being typed into the right panel's step-input (two distinct signals: the left-card bars are informational history, the step-input is the live input).
     - `returnItems` is built by two different methods sharing a common `buildProductMaps(mrr)` helper (required-qty-from-PO-line + received-qty-from-latest-receiptItem-row, deduped the same way as the backend/`generatePdf()`): **create mode** → `computeReturnItems(mrr)` additionally sums `alreadyReturnedByProduct` across `mrr.mrrReturns[].items[]` (mirrors the backend's incremental-return math) to compute both `remaining_quantity` and `already_returned_quantity`, defaults `return_quantity: 0`, and filters rows to `remaining_quantity > 0` (fully-returned products still don't show up in the picker — that filter is unchanged). **View mode** → `viewReturn()` maps the fetched `MrrReturn.items[]` directly, setting `remaining_quantity`/`already_returned_quantity`/`return_quantity` to that item's saved `returned_quantity`.
     - The small `{{return_quantity}}/{{received_quantity}}` label on each left-panel card still shows against `received_quantity` (unchanged, not part of this latest instruction — only the step-input's cap moved). `remaining_quantity` is what the backend hard-validates a submission against either way, so the step-input cap and the server cap are aligned again now.
     - `hasReturnQuantity` getter gates the Complete Return button (create mode only — at least one product must have `return_quantity > 0`).
  4. **Remarks** `ui5-textarea` (`remarks`, plain `[(ngModel)]` with `[rows]="2"` — **must be a number binding, not the plain `rows="2"` string attribute**, or Angular's NG2 template check fails since the underlying web component's `rows` property is typed `number`; `[readonly]="isViewMode"`; `FormsModule` comes via `SharedModule`).
  Footer: Complete Return button `*ngIf="!isViewMode"`; the Cancel/Close button is always present, text swaps via `[text]="isViewMode ? 'Close' : 'Cancel'"`, both call the same `closeDialog()`.
  All of `return_date`/`return_type`/`reason`/`remarks` are sent in the create-mode POST payload alongside `items`.
- `completeReturn()` → `POST store/mrr-returns { material_receipt_id, items, return_date, return_type, reason, remarks }`, on success toasts, closes dialog, reloads summary + list grid.

### Explicitly rejected during design (do not re-add without new instruction)
- "Change MRR" button — removed; combobox alone lets the user pick a different MRR.
- Logs tab/grid — removed; MRR activity logs are not surfaced here.
- Tab container — removed once only 2 sections remained (MRR select+info, then items).
- A separate read-only "View Details" dialog with its own tile-card + ag-grid layout — removed; the info button now opens the exact same dialog as "New Return" (see "Single shared dialog" above). Don't reintroduce a second dialog/template for viewing without a fresh instruction.
