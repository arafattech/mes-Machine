# Machine Overview Page (`/production/mco`) — End-to-End Enhancement Plan

> **Status as of 2026-07-07** — Phase 0 and most of Phase 1 below are **done**. This file is kept as the historical plan/rationale; for current, accurate state see:
> - [MISSING_INPUTS.md](MISSING_INPUTS.md) — precisely which DB fields/forms still need filling in, per tile
> - [docs/production-management/shared/MACHINE_OVERVIEW_COMPONENT_CONTEXT.md](../../../../../../../docs/production-management/shared/MACHINE_OVERVIEW_COMPONENT_CONTEXT.md) — current component behavior
>
> Done: date-range filter + charts wired to real `MachineStateEvents` (Phase 0); `MachineHasConfigs` specs, `MachineController::overview` endpoint (Availability/Performance/Quality/Efficiency, target/achieved/ok/waste), `machine_production_counts`/`machine_production_targets` schema + node-server writer (Phase 1). One bug found and fixed post-implementation: a `Carbon::diffInSeconds()` sign bug that zeroed Availability. A second issue was found in `MachineDurationService` (a state's "today" total doesn't include earlier same-day periods once the machine re-enters that state) — a fix was written and verified, then explicitly reverted at user request; current either/or behavior is intentional, see [MACHINE_DURATION_SERVICE_CONTEXT.md](../../../../../../../docs/production-management/shared/MACHINE_DURATION_SERVICE_CONTEXT.md).
> Not done: config-form fields for RPM/Temp/`ideal_cycle_seconds` (Phase 1, UI-only gap), the scrap/reject signal decision (Phase 1.5/3), and Phase 2 (RPM/temp acquisition, hardware-gated).

## Context

`MachineOverviewComponent` (`Frontend/src/app/modules/production-management/shared/components/machine-overview/machine-overview.component.ts`) is the machine detail page. Today it's a **UI shell**: only per-state durations (Active/Idle/Inactive/Maintenance, via `MachineDurationService` → real `MachineStateEvents` OData + socket.io `machine_status_runtime`) are real. Everything else is hardcoded in the component:

| Mock field | Feeds |
|---|---|
| `machineData.maxRpm/minRpm/maxTemp/minTemp` (3000/2500/100/20) | `MachineDetailsComponent` |
| `target/achieved/ok/total/waste` (72000/62000/72/80/160) | `ProductionOverviewComponent` |
| `runtime` (30-day array) | `LineChartComponent` |
| `datasets` (weekly Active/Idle/Inactive) | `BarChartComponent` |
| `metrics` (4 OEE tiles) | `QualityEfficiencyComponent` ×4 |
| `period` (fixed May 2024) | header label |
| `menuItems` | static, "Configuration" goes nowhere useful |

Goal: replace mock with real data end-to-end. The gap is uneven — some of it is buildable today with zero backend changes; the rest needs new Laravel schema and, for two fields, physical sensor wiring that's outside this codebase's control. Plan is phased accordingly so value ships incrementally instead of blocking on the hardest piece.

**Key architectural fact discovered during exploration:** Laravel and node-server share **one physical MySQL database** (`mes_lan`). node-server's Prisma schema is generated by `prisma db pull` against Laravel's schema — it does not own its own DB. Laravel migrations are the only source of DDL; after any new migration, node-server must run `npx prisma db pull && npx prisma generate` to pick it up. There is no "which DB does config live in" decision — config tables are literally the same rows read by both sides.

## Phase 0 — Ship now, zero backend changes

Only phase touching data that's real today (`MachineStateEvents`). Independent of everything else — do this regardless of how later phases land.

**0.1 — New `MachineRuntimeHistoryService`** (`.../shared/services/machine-runtime-history.service.ts`)
Separate from `MachineDurationService` (that one is a live "today" singleton snapshot — don't bolt historical range queries onto it). Export `MachineStateEventRow` from `machine-duration.service.ts` for reuse instead of redefining it.

- Query: `MachineStateEvents?$filter=machine_id eq {key} and started_at le {end} and (ended_at eq null or ended_at ge {start})&$orderby=started_at asc` — one request per window, includes rows that overlap the boundary (open row, or started before `start`). Confirmed: Lodata supports `or`/parenthesized `$filter` groups; no `$apply`/groupby support exists in the vendor package, so **bucketing happens client-side**; no server page cap (`pagination.max = null`) so no paging loop needed at this data volume.
- `getDailyActiveHours(machineKey, monthAnchor)` → `DayHours[]` for `LineChartComponent`. Clip each row to the window, split multi-day intervals at local-midnight boundaries (a shift crossing midnight must not be miscounted into one day), sum ACTIVE ms per day, convert to hours. Missing days can stay absent — `LineChartComponent`'s existing normalize/pad already fills 0 and clamps 0–24.
- `getWeeklyStateHours(machineKey, weekAnchor)` → `ChartDataset[]` (3 series: Active/Idle/Inactive — **not** Maintenance, matching current mock) for `BarChartComponent`. Same day-split, bucketed by weekday label. Reuse the exact current `borderColor`/`backgroundColor` triplet (lime/orange/red) so only the data source changes, not the visual.
- `getEventsInRange(machineKey, start, end)` → raw `MachineStateEventRow[]`, used by drill-down (0.3) and internally by the two aggregates above.

**0.2 — Fix `period`**
Replace `period = new Date(2024, 4, 1)` with a computed current-month anchor; derive `daysInMonth` from it instead of the hardcoded `30`. Drive both the line-chart title and `ProductionOverviewComponent`'s `periodLabel` off the same `period | date:'MMMM, y'` value instead of two independently hardcoded strings (component currently also hardcodes `'May, 2024'` separately for the overview tile).

**0.3 — Drill-down for `onDay`/`onPointClick`/`onPointHover`**
- Use `ui5-dialog` (existing app-wide modal pattern, e.g. `attachment-preview.component.html`) — no existing side-panel component in this module to justify introducing one.
- `onDay`/`onPointClick` resolve to a concrete date, call `getEventsInRange`, open dialog.
- Render rows via `AgGridTableComponent` with `AgGridTableCustomDataSourceConfig` (in-memory source) — keeps the "AG Grid for anything tabular" rule instead of hand-rolled rows. Columns: State/Start/End/Duration.
- `onPointHover`: both chart wrappers already configure a Chart.js tooltip on hover — confirm with stakeholder whether a real handler is even needed before building one; likely already satisfied.

**0.4 — Menu fix**
Route `'Configuration'` → `/base-data/machine-config` (real page, confirmed to exist) instead of `/production`. Gate visibility with `RolePermissionService.hasPermission(Permissions.BASE_DATA_MACHINE_CONFIG)` (same pattern as `layout.component.ts`) since it's a different permission group than this page's `PRODUCTION_ADMIN`. Note: neither that page nor `/base-data/machines` accepts a query param to pre-filter to one machine — deep-linking to *this* machine's config is a separate, small, cross-module change, out of scope here.

**0.5 — Scaffold `MachineOverviewDataService`** (`.../shared/services/machine-overview-data.service.ts`)
Consumption-side abstraction for Phase 1+2 data, built now so the future backend swap is a method-body change, not a component rewrite:

```ts
export interface MachineSpecs { maxRpm: number; minRpm: number; maxTemp: number; minTemp: number; }
export interface ProductionSummary { periodLabel: string; productionTarget: number; productionAchieved: number; machineOk: number; machineTotal: number; wastage: number; unit: string; }

@Injectable({ providedIn: 'root' })
export class MachineOverviewDataService {
  getSpecs(machineKey: string): Observable<MachineSpecs>;              // → of({3000,2500,100,20}) for now
  getProductionSummary(machineKey, period): Observable<ProductionSummary>; // → of(current mock numbers) for now
  getOeeMetrics(machineKey, period): Observable<Metric[]>;             // → of(current 4 mock tiles) for now
}
```

`MachineSpecs`/`ProductionSummary` go in the existing `.../shared/interface/interface.ts` next to `Metric`. Icon/color mapping (`box/cog/sparkles/wrench`, `green/purple/orange/rose`) is presentational — keep it as a private map inside this service, merged with whatever `value`/`delta` a future endpoint returns, so swapping backends never touches that visual mapping. `MachineOverviewComponent` switches to calling this service instead of holding the fields itself — identical rendered output, purely a refactor, zero regression risk, no need to wait on Phase 1.

## Phase 1 — Production counts + Availability/Performance/Quality (schema, no hardware)

**1.1 — Availability tile ships immediately, no new schema.** Computable today from `MachineStateEvents`: `active_seconds / total_seconds` over the window. Add a Laravel endpoint (below) that returns it now; wire `MachineOverviewDataService.getOeeMetrics` to it as soon as it exists.

**1.2 — Config bounds (`maxRpm/minRpm/maxTemp/minTemp`) — no new table needed.** `machine_has_configs` (migration `2026_03_02_065049_create_machine_has_configs_table.php`) **already has** `max_rpm/min_rpm/max_temp/min_temp` columns, already OData-exposed as `MachineHasConfigs`. `MachineOverviewDataService.getSpecs` just needs to query `MachineHasConfigs?$filter=machine_id eq {id} and is_active eq true&$select=max_rpm,min_rpm,max_temp,min_temp` instead of returning mock. **This alone de-mocks item 1 immediately — verify the config rows are actually populated for real machines before wiring.**

**1.3 — New schema for production counts + targets** (Laravel migrations → `prisma db pull`/`generate` in node-server):
- `machine_production_counts`: `id, machine_id (FK), work_order_id (FK work_orders, nullable), shift_id (FK employee_shifts, nullable), bucket_started_at, bucket_ended_at, good_count, scrap_count, total_count, timestamps`, index `(machine_id, bucket_started_at)`. Append-only bucketed history — replaces the lossy single-row upsert in node-server's current `machine_counters` (which has no history, overwritten every shot). Keep `machine_counters` untouched for the live cumulative needle.
- `machine_production_targets`: `id, machine_id (FK), work_order_id (FK, nullable), shift_id (FK, nullable), target_qty, effective_from, effective_to, is_active, timestamps`. Target must reference existing `work_orders`/`employee_shifts` — don't invent a standalone number; **open question for a human:** is target = `work_orders.quantity` prorated to shift, or an explicitly-entered value in this new table?

**1.4 — node-server writer** (`node-server/src/module/machine/runtime/machine.worker.ts`): replace the stubbed `handleGetStats` and upsert-only `saveCounter` with logic that also appends to `machine_production_counts` on shot events, bucketed by current shift/work-order (reuse existing shot-detection in `processSignals`).

**1.5 — Interim honesty on good/scrap:** no reject-counter signal exists anywhere in acquisition today. Ship with `total_count = shots, good_count = total, scrap_count = 0` (Quality tile reads 100%) rather than fabricating a split — real scrap counting is Phase 3, hardware-gated. Alternative: source scrap from `quality_inspections.defect_count` (already exists, no hardware needed) if manual QA entry is acceptable — **open question for a human**, decides whether Quality tile is hardware-blocked or ships in this phase.

**1.6 — OEE mapping:**
- Availability = durations (real, Phase 1.1).
- Performance = `(total_count / runtime) / ideal_cycle_time` — needs 1.3's counts + `machine_has_configs.taktzeit`.
- Quality = `good/total` — honest only once 1.5's scrap question is resolved.
- M/C Efficiency = Availability × Performance × Quality (the composite, not a 5th independent source).
- `machines.oee` (existing static decimal column): repurpose as a periodic rollup cache written by a scheduled job for fleet-list views, not read by this page — **open question:** confirm vs. drop entirely.

**1.7 — API contract:** one REST aggregation endpoint on `MachineController.php` (currently only has `machineAssociate`) — `GET /api/machines/{id}/overview?from&to` → `{target, achieved, ok, total, waste, oee:{availability,performance,quality,efficiency}}`. Preferred over multiple OData round-trips since Laravel can do the indexed `SUM`/date-window math in one place (`MachineOverviewService`, new). Add matching index on `machine_production_counts`.

## Phase 2 — RPM + temperature acquisition (hardware-gated)

Both gaps share the same root cause: **no analog register/named-field acquisition exists** — node-server only reads 5 discrete relay signals today.

- **RPM:** add optional `rpm_register`/`rpm_scale` columns to `machine_has_configs` (Laravel migration → prisma pull). Extend the channel poller (`node-server/src/module/machine/runtime/channel-mapping.service.ts`, `machine-runtime.types.ts`) to issue a `readHoldingRegisters` alongside the discrete reads when `rpm_register` is set; for API/MQTT-mode machines, extend the payload parser (`runtime/mqtt-channel-source.ts`) to read a named `rpm` field. Gate on existing `machines.has_rpm` capability flag.
- **Temperature (currently broken, always 0):** root cause confirmed in `node-server/src/module/machine/sync-engine/sync.machine.ts` — `insertToMysql` reads `data.value`, but the live worker payload (`machine.worker.ts`) has no `value` key at all, so `Number(undefined)` → `NaN` → coerced to `Decimal(0)`. This is the *same* underlying gap as RPM (no analog acquisition), not just a mapping bug — fixing the coercion alone can't invent a real reading. Fix: acquire via register/named-field (same mechanism as RPM), give it a stable payload key, and change `insertToMysql` to reject/skip non-finite values instead of silently writing 0.
- Schema: add `rpm` column to `machine_sensor_data` (simpler than generalizing to a long `(metric,value)` format, which would touch the existing OData entity's shape and readers) — **open question if the long format is preferred instead.**
- Throttle inserts (per `production-management/CLAUDE.md` scale mandate: 200+ machines, avoid unnecessary DB writes) — batch at the existing Redis→MySQL sync interval (10s), not per poll tick.
- **Hard external dependency, flagged explicitly:** requires each physical machine to expose a tachometer/temperature-sensor value on a readable register or in its protocol payload, and someone to supply the register map per machine. This is hardware/controls work, not just code — cannot be scheduled purely as a dev task.

## Phase 3 — Real scrap signal (hardware-gated, optional)

Only needed if Phase 1.5's interim (`scrap_count = 0`) or the manual `quality_inspections` route isn't sufficient long-term. Would add a dedicated reject-counter channel (same pattern as the existing shot-counter channel) — deferred until the Phase 1.5 decision is made.

## Open decisions needing a human call (surface before/while implementing)

1. Scrap counting: machine reject relay (hardware, Phase 3) vs. manual `quality_inspections.defect_count` (no hardware, ships in Phase 1) — decides if Quality tile is hardware-blocked.
2. Which machines physically expose RPM/temperature and their register maps — blocks Phase 2 per-machine, controls/hardware answer.
3. `machines.oee` — keep as scheduled rollup cache vs. deprecate for computed-on-read.
4. `machine_sensor_data` shape — add `rpm` column (simpler, recommended) vs. generalize to long format (more flexible, more churn).
5. Production target semantics — prorated from `work_orders.quantity` vs. explicit `machine_production_targets.target_qty` entry (affects whether a target-entry UI is needed).
6. Weekly bar chart: confirm 3-series (Active/Idle/Inactive, matches current mock) is intentional vs. adding Maintenance as a 4th.
7. `onPointHover`: confirm a real handler is wanted given Chart.js's built-in tooltip may already cover it.
