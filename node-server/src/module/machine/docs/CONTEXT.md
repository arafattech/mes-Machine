# Machine Module — Context

Real-time machine telemetry module for the `node-server` (NestJS) service. It polls shop-floor machines (Modbus TCP or HTTP/XML relay boards), derives production state, broadcasts live data to the Angular frontend over Socket.IO, and persists shot counters + a sensor-data history.

## 1. Responsibilities

1. **Acquire** raw 5-signal relay state from each enabled machine (Modbus or API transport, legacy mode) or channel `inputs` per PLC (API/MODBUS/MQTT, channel-mapping mode, default — §15).
2. **Derive** production state per poll tick (waiting / shot-start / running, shot counter, cycle times, heating state — legacy mode) or per-machine status from configured channels, debounced against flicker (channel-mapping mode — §15).
3. **Broadcast** the derived payload live to all connected frontend clients (`to_frontend`, batched — §7), and a dedicated `machine_status_runtime` event on each **confirmed** state transition (both acquisition modes).
4. **Persist** shot counters to MySQL (`machine_counters`), a time-series buffer to Redis + MySQL (`machine_sensor_data`), and state-transition history (`machine_state_events`, batched at scale — §9/§15).
5. **Self-heal**: worker isolation (legacy mode), capped worker-thread pool, auto-restart, hot config reload (Redis-cached both pipelines), per-PLC quarantine on repeated failure, persistent Modbus connections, stale-entry pruning on machine removal. See [`CHANGES_THIS_SESSION.md`](CHANGES_THIS_SESSION.md) for the full list of scale/reliability fixes and current-architecture flowcharts.

## 3. Data flow (the critical path)

Two acquisition pipelines exist, gated by `CHANNEL_MAPPING_ENABLED` (default `true`). Only one runs at a time. Full Mermaid flowcharts for both (plus the cross-repo config-invalidation flow) are in [`CHANGES_THIS_SESSION.md`](CHANGES_THIS_SESSION.md); this section is the condensed ASCII version.

### 3a. Channel-mapping mode (default)

```
        │
        ▼
watchTiers()  ── fixed cadence (CHANNEL_TIER_WATCH_MS) ──► bucket machines by
        │                                                   PLC-group cadence,
        │                                                   spin up new tier loops,
        │                                                   prune stale entries (§15)
        ▼
tierTick (one self-scheduling loop per cadence tier)
        │
        ▼
pollConfigs → acquireApi / acquireModbus (persistent conn, quarantined on repeat
        │      failure) / acquireMqtt (reads MqttChannelSource cache)
        ▼
deriveStatus(channels, lookup) ──► debounceStatus() (wall-clock, §15)
        │
        ├──► machineGateway.broadcastData / broadcastPlcStatus
        │        │
        │        ├─ emitToRoom('machine_<id>', 'message')      — immediate
        │        └─ pendingFrontendUpdates buffer               — flushed as one
        │                                                          array every
        │                                                          MACHINE_FRONTEND_BROADCAST_MS
        │                                                          → socket 'to_frontend'
        │
        └──► (confirmed transition only) persistTransitions()
                 → MachineStateTracker.recordTransitions()  (batched: 1 findMany +
                    1 raw UPDATE + 1 createMany) → machine_state_events
                    → socket 'machine_status_runtime'
```

```
   machine-runtime.service.ts  worker.on('message')
        │

        ├─ 'connection'→ broadcastPlcStatus + postMessage('pause'/'resume')

                          run in send order against this service's one shared

                               │
```

## 4. Signal acquisition

Every machine exposes **5 discrete inputs**, in fixed order:

| Index | Signal | Meaning                               |
| ----- | ------ | ------------------------------------- |
| 0     | `F`    | Fault / Fehler                        |
| 1     | `P`    | Production (part produced this cycle) |
| 2     | `A`    | Automatic mode active                 |
| 3     | `ZH`   | Heating signal                        |
| 4     | `HK`   | Heating element                       |

Two transports produce this `number[5]`:

- **Modbus** (`createModbusTransport`): `readDiscreteInputs(0, 5)` over TCP port 502. Poll interval + connect timeout are **per-machine** (see §11): interval = `poll_interval_ms` else 1000 ms; connect guarded by `request_timeout_ms` else 3000 ms (`setTimeout` on the socket, disabled once connected so idle gaps never drop a live connection). Exponential-backoff reconnect (1s → 30s, max 20 retries → `onDead`).
- **API** (`createApiTransport`): HTTP GET an XML/relay endpoint. Poll interval + request timeout are **per-machine** (see §11): interval = `poll_interval_ms` else `MACHINE_PULL_DURATION` (default 2000); request timeout = `request_timeout_ms` else 3000 ms. `parseRelayStates` tolerates many shapes — `<inputNstate>`, `<relayNstate>`, namespaced variants, `key=value`, and plain `[0,1,...]` arrays. A configurable `api_signal_map` maps relay index → signal (default `{F:1, P:2, A:3, ZH:4, HK:5}`). 20 consecutive errors → `onDead`.

`applyInversion` XORs each signal with its per-machine invert flag (wiring may be active-low).

## 5. State machine (`processSignals`)

Per tick, after inversion:

```
faultEdge = (F==1 && lastFault==0) ? 1 : 0      // RISING EDGE only

if (automatic == 1):
    cycleTime += 1
    if (production==1 && lastProduction==0):     // new shot detected
        shotNr        += 1
        lastCycleTime  = cycleTime
        cycleTime      = 0
        state = 'S'  (SHOT_START)  → saveCounter()
    else:
        state = 'M'  (RUNNING)
else:
    cycleTime += 1
    state = 'W'  (WAITING)

running = (lastCycleTime > 0 && lastCycleTime <= taktzeit) ? 1 : 0
heating: if (ZH||HK) and no heatingStart → set heatingStart=now (+DB)
         if (!ZH && !HK) and heatingStart → clear (+DB)
```

State codes: `W` = waiting, `S` = shot-start (single tick), `M` = running.

This is the exact object the frontend receives. **Source: `machine.worker.ts` `processSignals` emit block.**

| Field       | Worker source   | Type         | Meaning                                           | Notes                                                           |
| ----------- | --------------- | ------------ | ------------------------------------------------- | --------------------------------------------------------------- |
| `MNR`       | `cfg.id`        | string       | Machine number / config id                        | Used as room + map key                                          |
| `transport` | `cfg.transport` | string       | `'modbus'` \| `'api'`                             | data source                                                     |
| `F`         | `faultEdge`     | 0\|1         | Fault **rising edge**                             | 1 for a single tick on 0→1 only; **not** a sustained fault flag |
| `P`         | `production`    | 0\|1         | Production relay (inverted)                       |                                                                 |
| `I`         | `machineState`  | string       | State: `W` waiting / `S` shot-start / `M` running |                                                                 |
| `C`         | `lastCycleTime` | number       | Last completed cycle, **seconds**                 |                                                                 |
| `A`         | `automatic`     | 0\|1         | Automatic mode                                    | drives frontend ACTIVE status                                   |
| `ZH`        | `zh`            | 0\|1         | Heating signal relay                              |                                                                 |
| `HK`        | `hk`            | 0\|1         | Heating element relay                             |                                                                 |
| `R`         | `running`       | 0\|1         | Derived: `lastCycleTime>0 && ≤ taktzeit`          |                                                                 |
| `S`         | `shotNr`        | number       | **Cumulative shot counter**                       | not speed/rpm                                                   |
| `T`         | `cycleTime`     | number       | **Current elapsed cycle, seconds**                | not temperature                                                 |
| `TZ`        | `avgTZ`         | number       | Avg cycle time                                    | **STUB — always 0** (`handleGetStats`)                          |

| `Bad`       | `bad`           | string       | Scrap list (JSON string)                          | **STUB — always `'[]'`**                                        |

There is **no temperature, rpm, load, or hours field** in this stream. The frontend `machine-board.component.ts` currently mis-labels `T`→`temp`/`hours` and `S`→`rpm`/`load` (see §9).

## 9. Persistence

### MySQL (via Prisma)

| Table                       | Written by                                                                                                                                                                                                                                        | Columns touched                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `machine_counters`          | worker `postMessage('save_counter')` → `MachineRuntimeService.handleSaveCounter` (against the shared `PrismaService`, not a worker-local client), serialized per machine                                                                          | `masch_id, shot_nr, last_cycle_time, cycle_time`                                       |
| `machine_has_configs`       | worker `postMessage('set_heating_start'/'clear_heating_start')` → `handleSetHeatingStart`/`handleClearHeatingStart`, serialized per machine                                                                                                       | `heating_start` (where `machine_id`, `is_active`)                                      |
| `machine_production_counts` | worker `postMessage('record_production_shot')` → `handleRecordProductionShot`, serialized per machine                                                                                                                                             | `machine_id, bucket_started_at, bucket_ended_at, good_count, scrap_count, total_count` |
| `machine_sensor_data`       | `sync.machine.insertToMysql`                                                                                                                                                                                                                      | `machine_id, timestamp, temperature`                                                   |
| `machine_state_events`      | `machine-state-tracker.service` — `recordTransition` (single-machine, legacy path via `trackLegacyState`/`deriveLegacyState`) or `recordTransitions` (batched, channel-mapping path via `persistTransitions`), on each **confirmed** state change | `machine_id, state, started_at, ended_at, duration_seconds`                            |
| `machines`                  | read-only (`resolveMachineId`)                                                                                                                                                                                                                    | resolve `custom_id`/`id` → `id`                                                        |

Per-machine writes relayed from a worker (`save_counter`/`set_heating_start`/`clear_heating_start`/`record_production_shot`) are serialized in send order by `MachineRuntimeService.serializeWrite` — a fire-and-forget `postMessage` relay gives no ordering guarantee across overlapping async calls on its own, so without this, two rapid writes for the same machine could race and the slower one could clobber the faster one's result. `get_counter` is the one relayed operation that round-trips a response (`counter_result`) — on any DB error it still replies (with `counter: null`, falling back to "no row yet") so the worker's `loadInitialState()` never hangs waiting for a reply that never comes.

Config reads (`machine-config.service.loadConfigs`): `machine_has_configs` (id, ip_plc, heating_start, live_status_api, `server_call_sec`, `timeout_sec`, `read_from`), `machine_signals` (invert flags), `machine_transport_configs` (transport, api_url, api_signal_map — legacy shot-counting pipeline only, independent of `read_from`), `config_has_channels` (channel→status rows, joined by `config_id` = `machine_has_configs.id`). `server_call_sec`/`timeout_sec` are seconds; the loader converts >0 values to ms (`resolveMs`), else null → env/hardcoded fallback.

### Redis (`sync.machine.ts`)

- **Stream** `mysql:machine_data` — append on ingest (`xadd`), consumed by group `mysql-sync` / consumer `worker-1` every `MACHINE_DATA_ACTION_DURATION` ms (default 10000). Each message → `insertToMysql` → `xack`. Trimmed `MAXLEN ~ 5000`.
- **Sorted set** `machine:buffer:<id>` — score = epoch ms, member = JSON payload. Trimmed to last 10 min, TTL 15 min. Read by the GET endpoint.

> **Shape mismatch (known):** `socketToRedis` / `insertToMysql` read `data.status`, `data.value`, `data.timestamp` and map `value`→`temperature`. The worker's `to_frontend` payload has none of those keys. So: (a) the live worker payload is never persisted to `machine_sensor_data`; (b) any ingest forwarding the relay-shaped payload through `POST /machine_data` or `from_pie` persists `temperature = 0`. The sensor-data path was designed for a `{machineId, status, value, timestamp}` sensor shape, not the relay telemetry.

## 10. Worker orchestration (`machine-runtime.service.ts`)

Only active in legacy mode (`CHANNEL_MAPPING_ENABLED=false`) — the channel poller (§15) owns status polling otherwise.

- **Spawn:** `enqueueWorker(config)` per config on boot, staggered by `MACHINE_SPAWN_STAGGER` ms. Spawns immediately if `workers.size < MACHINE_MAX_CONCURRENT_WORKERS`, else pushes to a `pendingWorkerConfigs` queue; a freed slot (worker stopped/removed) promotes the next queued config (`promoteQueuedWorker`). The cap defaults high (1000, matching the module's own stated future scale) — it's a safety ceiling against a misconfigured thread-spawn storm, not a throttle on real deployments. Prefers compiled `machine.worker.js`; falls back to `.ts` via `ts-node/register` + `tsconfig-paths/register`.
- **Bridge:** worker `data`→`broadcastData` **and** `trackLegacyState` (see below); `dead`→`broadcastPlcStatus(false, dead=true)`; `connection`→`broadcastPlcStatus(connected)` + `postMessage('pause'/'resume')` (replaces the old ping subprocess, see below); `error`→log; DB-op messages (`get_counter`/`save_counter`/`set_heating_start`/`clear_heating_start`/`record_production_shot`)→relayed to this service's own shared `PrismaService` handlers, per-machine writes serialized (§9).
- **Restart:** non-zero exit → respawn with exponential backoff (1s → `MACHINE_MAX_RESTART`, default 30000). Clean exit (code 0) → drop + `promoteQueuedWorker`.
- **Hot reload** (`syncWorkerConfigs`, every `MACHINE_WATCH_MS`, config Redis-cached via `loadConfigs()` — §11): diffs fresh configs vs running — enqueues new machines (respecting the concurrency cap), stops removed ones (+ promotes a queued replacement), prunes `pendingWorkerConfigs`/`lastState`/`pendingWrites` for machines no longer in config and calls `machineGateway.forgetMachine(id)`, and posts `config_update` / `ip_change` / `url_change` control messages for `taktzeit`, `heating_start`, invert flags, `poll_interval_ms`, `request_timeout_ms`, ip, api_url changes. A `config_update` carrying `poll_interval_ms`/`request_timeout_ms` makes the worker **rebuild its transport** (`restartTransport`), since interval/timeout are captured at transport creation.
- **PLC reachability (no subprocess):** the old OS `ping`-per-machine check (`MACHINE_PING_MS`/`PING_MS`) was removed outright. `createModbusTransport` now fires an `onConnectionChange(connected)` callback on its own real connect/disconnect edges (not the deliberate reset inside `updateIp`), relayed to the main thread as a `'connection'` message — a persistent connection's own state is a stronger, cheaper reachability signal than a redundant ICMP probe. Same external behavior as before (`broadcastPlcStatus` + `pause`/`resume`), just sourced differently. API-transport machines were never ping-checked either way (ping was always Modbus-only).

Worker control messages (in): `stop | pause | resume | config_update | ip_change | url_change | counter_result`.
Worker messages (out, beyond `data`/`dead`/`error`): `connection | get_counter | save_counter | set_heating_start | clear_heating_start | record_production_shot`.

**Legacy-mode state persistence:** the worker payload has no `STATUS` field, so `MachineRuntimeService.deriveLegacyState(payload)` derives one from the raw flags — `A===1 → active`, `P===1 → idle`, else `inactive` (mirrors the frontend's `deriveActivity()` fallback; **no `maintenance`** — the worker telemetry has no maintenance signal, unlike channel mapping mode, §15). A local `lastState` Map (same fast-path-cache pattern as `ChannelMappingService`) diffs on every `data` tick; on a real change, `trackLegacyState` calls the shared `MachineStateTrackerService.recordTransition`. `machine_state_events` and `machine_status_runtime` are not channel-mapping-exclusive — both acquisition modes persist and broadcast identically. This does not touch `broadcastData`/`to_frontend` — that telemetry stream is unchanged (aside from the batching in §7).

**No `PrismaClient` in the worker thread:** every DB read/write the worker used to perform directly (`machine_counters`, `machine_has_configs.heating_start`, `machine_production_counts`) is now a `postMessage` to the main thread instead. `get_counter` (used once, at `loadInitialState()`) is the only one that needs a reply — correlated by a per-request ID, resolved by a `counter_result` message. The rest (`save_counter`, `set_heating_start`, `clear_heating_start`, `record_production_shot`) are fire-and-forget. This means 200+ machines in legacy mode share **one** Prisma connection pool instead of one independent pool per worker thread (each defaulting to `num_cpus*2+1` connections) — previously the module's hardest scaling wall.

## 11. Configuration resolution (`machine-config.service.ts`)

`loadConfigs()` (legacy pipeline) and `loadChannelConfigs()` (channel poller) both merge, per machine, in priority order:

```
machines.json override  >  DB row  >  hardcoded default
```

- Override file: `<cwd>/src/module/machine/machines.json` (array; keyed by `id`). Optional — missing/invalid file is ignored. See `machines.example.json` for the shape. Override keys mirror DB names (`server_call_sec`, `timeout_sec` in seconds; `channels`; `read_from`).
- DB sources joined by machine id: `machine_has_configs` + `machine_signals` + `machine_transport_configs` + `config_has_channels`.
- Resolved `MachineRuntimeConfig`: `{id, ip, taktzeit(default 999), heating_start, enabled, transport, api_url, api_signal_map, invert{F,P,A,ZH,HK}, poll_interval_ms, request_timeout_ms, live_status_api, channels[], channel_read_from}`.
  - `poll_interval_ms` ← `server_call_sec`×1000, `request_timeout_ms` ← `timeout_sec`×1000; `null` when unset/≤0 → consumer applies its default.
  - `channels`: `{channel_id, status}[]` from `config_has_channels` (`status` ∈ `active|inactive|maintenance|idle`). `channel_id` is the PLC digital-input index (0-9, i.e. `DI0`..`DI9`) — it doubles directly as the index into the PLC's `inputs[]` array, no physical-pin translation needed.
  - `channel_read_from`: `'MQTT'|'API'|'MODBUS'`, normalized from `read_from` (unrecognized/empty → `'API'`, warned once at load if a non-empty value was rejected). Selects which transport `ChannelMappingService` uses to acquire `channels`' live inputs — independent of `transport` (legacy shot-counting pipeline). API/MODBUS always group/key by `ip` (`ip_plc`) — machines sharing one PLC share one acquired reading. MQTT can key by `ip` **or** `id_iot` (`machine_has_configs.id_iot`) instead, for firmware that publishes by a stable device ID rather than a DHCP-assigned IP — see §15.
- Only `enabled` configs are returned.

### `loadChannelConfigs()` — Redis-cached lean config (channel poller only)

`ChannelMappingService` calls `loadChannelConfigs()` instead of `loadConfigs()` — it runs every poll tick (as fast as ~2s), so hitting MySQL's 4-table join on every tick would be wasteful for data that rarely changes. Instead:

1. Try `redis.get('machine:channel_configs')`. On hit, parse the cached **raw** (pre-override) rows.
2. On miss (or a Redis error — logged and treated as a miss, fails open): run 2 lean Prisma queries only — `machine_has_configs` (id, machine_id, ip_plc, live_status_api, server_call_sec, timeout_sec, read_from) + `config_has_channels` — build the raw rows, then `redis.set(key, JSON.stringify(rows), 'PX', MACHINE_CONFIG_CACHE_TTL_MS)` (default 10000ms). A failed `SET` is non-fatal — just means the next tick re-queries MySQL.
3. `machines.json` overrides are **always** applied fresh on top of the raw rows (cached or freshly-queried) — override values are local to this node-server instance and are never written into the shared Redis cache.
4. Returns `ChannelRuntimeConfig[]` (the lean type, §1) — deliberately excludes `invert`, `transport`/`api_url`/`api_signal_map`, `heating_start`, `taktzeit`, `enabled` (filtered via the `is_active` DB `where` clause instead), none of which channel status derivation needs.

Reuses the same Redis client (`GetRedisClient()` from `config/redis/config.redis.ts`) already used by `sync-engine/sync.machine.ts` — no new Redis module. **Gotcha for future edits:** `machine_has_configs.id` / `config_has_channels.config_id` are Prisma `BigInt` — only their `String(...)`-coerced values are ever put into the cached row object, never the raw `BigInt`, or `JSON.stringify` throws.

### `loadConfigs()` — Redis-cached full config (legacy pipeline)

`MachineRuntimeService.syncWorkerConfigs` (§10) polls this every `MACHINE_WATCH_MS` (default 30s) — without a cache that's a full 4-table join (`machine_has_configs` + `machine_signals` + `machine_transport_configs` + `config_has_channels`) every cycle, regardless of whether anything changed. Same cache-first pattern as `loadChannelConfigs()` above, its own key (`machine:runtime_configs`) and cached raw-row type (`RawFullRow` — `RawLeanRow` plus invert flags + shot-counting transport fields), same TTL (`MACHINE_CONFIG_CACHE_TTL_MS`). `machines.json` overrides are, again, always applied fresh on top of the cached rows, never cached themselves. The channel-map-building loop is shared between both raw-row fetchers via a private `buildChannelMap` helper.

### Event-driven invalidation (both caches)

Both `machine:channel_configs` and `machine:runtime_configs` are TTL-bound, but not TTL-_only_ — the Laravel backend (`Backend/app/Http/Controllers/MachineConfigController.php`) deletes both keys via `MachineConfigCacheInvalidator` right after its `store()`/`update()` transactions commit, using a dedicated `shared_cache` Redis connection (`Backend/config/database.php`) with prefixing disabled so it targets the exact unprefixed keys this service reads (the `default` Laravel connection's `laravel_database_` prefix would otherwise silently miss). A config edit reaches the next poll tick instead of waiting out the TTL; a failed Redis delete just logs a warning and falls back to the TTL, never fails the save.

## 13. Known issues / tech debt

1. **Frontend field mapping wrong** (`machine-board.component.ts`): `temp`/`hours` both ← `T` (cycle seconds), `rpm`/`load` both ← `S` (shot count). `overallEfficiency` = last machine's `S` → renders raw shot count as a percentage (e.g. "202%"). No temperature exists in the stream.
2. **Sensor-data shape mismatch** (§9) — `temperature` persists as 0; live payload never reaches `machine_sensor_data`.
3. **Stats are stubs** — `handleGetStats` hardcodes `TZ/Total/Bad`; `R`, `I` carry the real activity signal but the frontend ignores them.
4. **`F` is edge-only** — sustained faults are not representable in the broadcast payload.
5. **Machine status is now a fully dynamic, admin-configurable vocabulary in channel-mapping mode** (§15) — sourced from `machine_states`/`machine_has_states`, not a hardcoded 5-value set. The legacy worker telemetry stream (`machine.worker.ts`'s `to_frontend` payload, §6) is unaffected and still only carries the raw `A`/`P` flags — `MachineRuntimeService.deriveLegacyState` maps those to a fixed 3-value subset (`active`/`idle`/`inactive`) resolved to the matching `machine_states` row by name, since the legacy path has no per-channel config to derive an arbitrary state from. This is a documented permanent boundary, not a gap to close — see §15's Fault-inference note for the other explicit behavior change from this rework.
6. Commented-out demo/log blocks remain in the worker, runtime, and config service.
7. **`machine_state_events` has no archival/retention strategy** — every transition, for every machine, forever, in one un-partitioned table. Deliberately deferred this session (needs a new archive/rollup table + migration + a retention-window decision) — see [`CHANGES_THIS_SESSION.md`](CHANGES_THIS_SESSION.md) §13.
8. **Legacy worker mode may be pure dead weight in this deployment** — production `.env` has `CHANNEL_MAPPING_ENABLED=true` and there's no `machines.json` override forcing legacy transport. If no machine genuinely needs an isolated persistent connection outside the shared-PLC-group model, the whole worker-thread pipeline (`machine.worker.ts`, most of `machine-runtime.service.ts`) is a candidate for deletion, not just hardening. Not yet confirmed/acted on.
9. **No cross-transport dedup per physical PLC — mixed `read_from` on one IP causes concurrent HTTP+Modbus hits and can crash the device.** `acquireApi`/`acquireModbus`/`acquireMqtt` each dedupe _within_ their own partition (one HTTP GET per unique IP in the API group, one persistent connection per unique IP in the MODBUS group), but nothing dedupes _across_ partitions — if `machine_has_configs` rows sharing one `ip_plc` disagree on `read_from` (e.g. 4 machines say `MODBUS`, 1 says `API`, all same IP), that one physical device gets hit by both an HTTP request and a Modbus TCP read **concurrently, every tick**. Observed in production against an ESP32-P4 (`PROTOCOLS_DATA.md`): the HTTP connection resets (`socket hang up`) and the Modbus read fails (non-`Error` rejection, logs as `[object Object]`) in the same tick window, repeatedly, eventually quarantining the PLC. Root cause was config data (inconsistent `read_from` across rows sharing an IP), not a code bug — fix is operational: keep `read_from` consistent for every machine on the same `ip_plc`. **Detection guard added:** `ChannelMappingService.warnOnReadFromConflicts` (called once per tier tick, from `pollConfigs`, before partitioning by transport) groups that tick's configs by `ip` (MQTT excluded — it never sends the device a request, so it can't collide) and logs a warning the first time an IP's machines disagree on API vs MODBUS, going quiet on that IP once resolved. Same-IP API/MODBUS machines are always tiered together (`buildIpCadenceMs` ignores `channel_read_from`), so one tier's config set is guaranteed to contain the full picture for any given IP — this is detection/alerting only, still no automatic dedup or transport arbitration, so the fix when it fires is still operational (align `read_from` for every machine on that `ip_plc`).

## 15. Channel mapping mode (`channel-mapping.service.ts`)

Default status pipeline, gated by `CHANNEL_MAPPING_ENABLED!=='false'` (on unless explicitly disabled). When on, `MachineRuntimeService` spawns **no workers**; `ChannelMappingService` owns status polling for every machine, regardless of transport. This is independent of the legacy per-machine worker's shot-counting/heating pipeline (`machine_transport_configs.transport`), which is untouched by any of this.

**Why:** many machines share one PLC, and different machine hardware exposes its channel state over different transports (HTTP JSON, Modbus TCP, or MQTT publish). This mode dedupes acquisition per PLC/broker instead of once per machine, then derives each machine's status from its own configured channels.

**Cadence tiering (`watchTiers`/`tierTick`/`pollTier`):** machines are bucketed into independent cadence tiers instead of one global tick at the fastest machine's cadence. `buildIpCadenceMs` computes, per PLC IP, the **fastest** `poll_interval_ms` among all machines sharing that IP (API/MODBUS configs are grouped/fetched per IP — two machines on one PLC with different configured cadences must still land in the _same_ tier, or two tier loops would poll the same connection concurrently); `resolveTierMs` buckets each config into the smallest `CHANNEL_CADENCE_TIERS_MS` bucket that satisfies that cadence (MQTT machines, no shared connection to align, are bucketed individually). A fixed-cadence watcher (`CHANNEL_TIER_WATCH_MS`, independent of any machine's own cadence) starts a new self-scheduling `tierTick` loop for any tier that appears, and a tier loop stops itself when its last machine leaves (the watcher restarts it if machines return). DB cadence edits take effect on that tier's next tick — no restart.

**Per tier tick (`pollTier` → `pollConfigs`):**

1. `loadChannelConfigs()` (Redis-cached, lean — see §11) → filter to configs with `channels.length > 0` **and** belonging to this tier, then partition by `channel_read_from` (`'API' | 'MODBUS' | 'MQTT'`, from `read_from`).
2. Acquire each partition's `inputs` **and**, if `CHANNEL_READ_COUNTS=true` (env, default `false`, checked independently by `ChannelMappingService` and `MqttChannelSource`), `counts` in parallel (`ChannelAcquisition = {lookup, inputs, counts}`, `channel-lookup.util.ts`). When the flag is off, `counts` is a 10-zero array on every transport and no counter-specific work happens (no register decode, no extra parsing, and on Modbus no extra network call at all):
   - **API** (`acquireApi`): one HTTP GET per unique PLC IP (`groupByPlc`/`fetchPlcTracked`). PLC must return JSON `{ inputs: boolean[], counts: number[] }` (see `PROTOCOLS_DATA.md`) — with the flag on, a missing/invalid `counts` array is tolerated (warned, defaults to 10 zeros via `buildChannelCounters`); a missing `inputs` array always fails the whole poll for that PLC (`null`), since status derivation needs it regardless of the flag. URL = `live_status_api` (if absolute) else `http://<ip><CHANNEL_PLC_STATUS_PATH>`.
   - **MODBUS** (`acquireModbus`): a **persistent** Modbus TCP connection per unique PLC IP (`groupByModbusIp`/`readModbusInputsTracked`/`connectModbus`) — connect once, `readDiscreteInputs(0, 10)` (FC2, DI states) on `CHANNEL_MODBUS_PORT` (default 502) on every subsequent tick, reconnecting transparently on any error/close/read-failure. **Only with `CHANNEL_READ_COUNTS=true`** does it also issue `readInputRegisters(0, 20)` (FC4, 10×32-bit counters, low word first — `decodeModbusCounters`) — a genuine second round trip per PLC per tick, so it's opt-in rather than unconditional (most fleets have no channel in Counter mode). The two reads are independent: a counter-read failure alone (discrete-input read still OK) falls back to 10 zero counts with a warn, rather than failing the whole poll — status derivation only needs `inputs`. Same connect-once/read-on-tick model the legacy worker's own Modbus transport already used — no more connect/teardown every tick.
   - **MQTT** (`acquireMqtt`): no network call either way — synchronously reads `MqttChannelSource.getLatestForMachine(ip, idIot)`, a cache fed by a persistent subscription (see below); the cached payload already carries both `inputs` and `counts` from the same published JSON message (`counts` only extracted/logged when the flag is on — always free either way since it's the same message).
   - Both API and Modbus acquisition go through **PLC quarantine** first (`isPlcQuarantined`/`recordPlcResult`): a PLC past `CHANNEL_PLC_MAX_FAILURES` consecutive failures is skipped entirely (no connect attempt, no timeout wait) for `CHANNEL_PLC_QUARANTINE_MS` — a success at any point clears it.
3. `inputs[i]` → `{i: boolean}` lookup (`buildChannelLookup`, `channel-lookup.util.ts`) — channel `i` (`DI{i}`) is the input array index directly, no physical-pin translation needed, for all three transports. `counts[i]` stays a plain `number[]`, same index convention — it isn't looked up per-status-channel like `inputs` is (no `config_has_channels` "counter" purpose exists), it's just carried through raw for any consumer to read by DI index.
4. Per machine, `deriveStatus(channels, lookup, statesById, defaultStateId, roles)` gives a **raw candidate** `{stateId, channel}`, which is passed through `debounceStatus()` (see below) before being treated as real; the resolved `stateId`'s name (from `machine_states`, via the same Redis-cached `loadMachineStatesMap()` config path — no extra per-tick DB query) is broadcast as `STATUS`, alongside `machine_state_id` itself and a `lastSeenAt` timestamp (below): `{MNR, STATUS, machine_state_id, channel, source:'channel', inputs, counts, lastSeenAt}` (the **debounced** status, plus the raw acquisition arrays — `null` for both when the machine's PLC is offline this tick) via `broadcastData` + `broadcastPlcStatus`. `source` is always `'channel'` regardless of transport — the frontend doesn't distinguish. Frontend reads `STATUS` (`machine-board.component.ts`, by name) and `machine_state_id` (services that need the numeric FK, e.g. `MachineDurationService`); `inputs`/`counts` are broadcast but not yet consumed by any frontend component as of this writing.
   - **`lastSeenAt`** (epoch ms, or `null` if never acquired): the last time this machine's PLC _actually_ returned real data — deliberately **not** `Date.now()` on every tick (this object is assembled every tick regardless of online/offline, so that would always read "just now" even for a dead PLC, defeating the purpose). Sourced per transport: MQTT → `MqttChannelSource.getLastReceivedAt(ip, idIot)` (raw cache timestamp, bypassing the `stalenessMs` gate `getLatestForMachine` applies); API/MODBUS → a new `lastSuccessAt: Map<string, number>` (keyed by PLC `ip`, same key as `plcHealth`), set inside `recordPlcResult` only on `success === true`. Consumed by the Angular `MachineDurationService`, which has its own `to_frontend` subscription just for this field, folded into `snapshot()`'s `lastSeenAt` — see the frontend's [MACHINE_DURATION_SERVICE_CONTEXT.md](../../../../../Frontend/docs/production-management/shared/MACHINE_DURATION_SERVICE_CONTEXT.md). Exists specifically so the board/overview UI can tell a legitimately idle-but-connected machine apart from a genuinely silent/offline one — both resolve to the same `Inactive` `STATUS` (see the `deriveStatus` note below), but only one of them has a `lastSeenAt` that keeps advancing.
5. Once per tick (not per PLC-group), `watchTiers` also runs `pruneStaleEntries` — see the map-pruning paragraph below.

**Status derivation (`deriveStatus`)** — genuinely arbitrary, admin-configured N-state model, replacing what used to be a hardcoded 2–3-channel truth table (`maintenance`/`active`/`idle` fixed channel purposes). Each configured channel is tagged with one `machine_state_id` (an admin-defined row in `machine_states`, not a fixed enum) instead of a hardcoded string purpose:

1. Collect every channel reading HIGH → the set of _candidate_ state ids, via each channel's tagged `machine_state_id` (`config_has_channels.machine_state_id`).
2. If candidates exist, the winner is whichever has the highest `machine_states.priority` — replaces the old fixed if/else-if precedence (previously effectively Maintenance > Active > Idle, Fault as a special case).
3. If **no** channel reads HIGH, fall back to this machine's designated default state — `machine_has_states.is_default` (exactly one `true` per machine, enforced at the application layer in `MachineController::machineAssociate`) — replaces the old hardcoded `else → INACTIVE`. `null` if the admin hasn't designated one yet (a machine that predates this rework and has never been re-tagged has no default and resolves to `null`/no status on total silence).

**Fault sensor-contradiction detection is preserved** (`detectContradictionFault`), restored after briefly being dropped during the initial priority-model rewrite. Resolved by state _name_ ("active"/"idle"/"fault", case-insensitive), not a hardcoded channel index — a no-op for any machine that hasn't tagged all three of those state names. When this machine has at least one channel tagged "Active" and one tagged "Idle": if any Active-tagged channel reads HIGH while every Idle-tagged channel reads LOW, that's treated as a Fault _candidate_ at Fault's own configured `priority`, competing against whatever channel-HIGH candidate the normal per-channel loop already found — so e.g. Maintenance still wins if its priority is higher, same precedence as the old hardcoded truth table. A machine can still explicitly wire a dedicated Fault-detection channel instead/in addition — that candidate competes on priority exactly like any other tagged channel. Only a machine missing "Active", "Idle", or "Fault" from its `machine_states` vocabulary entirely gets no contradiction check (nothing to compare/resolve to).

**Performance: role ids resolved once per tick, not once per machine (`resolveStatusRoles`).** `deriveStatus`'s default-fallback ("no candidate, resolve to Inactive") and `detectContradictionFault` both need the active/idle/fault/inactive state ids by name. Originally each looked this up itself via `for (const meta of statesById.values())` — a full linear scan of `statesById`, repeated **once per machine, every tick**, even though `statesById` is identical for every machine in a given tick (it's the same Redis-cached snapshot for the whole poll). `pollConfigs` now calls `resolveStatusRoles(statesById)` exactly once per tick, right after `statesById` resolves, producing a small `{ activeId, idleId, faultMeta, inactiveId }` object passed into both `deriveStatus` and `detectContradictionFault` for every machine in that tick's loop. Same "last match wins" semantics as before (Map iteration order is insertion order from `loadMachineStatesMap`) — pure hoisting, no behavior change, verified via identical before/after API output for the same machine state.

**Status debounce (`debounceStatus`):** a candidate status must hold for `CHANNEL_STATUS_DEBOUNCE_MS` **wall-clock** time (not tick count — tiers run at different cadences, so a tick-based counter would mean a different real debounce window per tier) before it overwrites the confirmed value used for both broadcast and persistence. A brand-new machine's first-ever reading is trusted immediately (no startup lag). This filters contact-bounce/electrical-noise flicker on raw digital inputs, which would otherwise both spam `machine_state_events` writes and pollute the uptime/OEE data those durations feed — see the tradeoff note at the end of this section.

**MQTT channel source (`mqtt-channel-source.ts`):** MQTT is pub/sub, not poll-based, so it doesn't fit the tick-driven fetch model above — a single shared client connects once (`MQTT_BROKER_URL`), covering every MQTT-mode machine over that one connection rather than one connection per machine. The device identifier can be **either** `ip` or `id_iot` (`machine_has_configs.id_iot` — for firmware that publishes by a stable device ID rather than a DHCP-assigned IP), selected consistently across topic subscription, per-message extraction, and cache lookup:

- **Per-device `{ip}` topic** (e.g. `machines/{ip}/status`): subscribes once with that segment replaced by `+` (broker-wide wildcard); the match value is read from that topic segment on each incoming message. Passive — receives every message on the matching topic shape regardless of DB config (see the "Important" note below).
- **Per-device `{id_iot}` topic** (e.g. `devices/{id_iot}/status`, or the bare `{id_iot}` template this deployment uses since `machine_has_configs.id_iot` here already stores the **full literal topic string**, e.g. `machine/status`, `plc-2/status` — not a bare device ID): **not** a wildcard. `MqttChannelSource` injects `MachineConfigService` and, on connect and then every `MQTT_TOPIC_WATCH_MS`, calls `loadChannelConfigs()` (§11 — the same Redis-cached rows `ChannelMappingService` already polls, so this adds no extra Prisma query) to get the current set of `id_iot` values for machines with `read_from='MQTT'`. It builds one literal topic per device, diffs that set against what's currently subscribed, `subscribe()`s newly-added topics and `unsubscribe()`s + evicts the cache entry for removed ones. Because `machine:channel_configs` is invalidated on write by the Laravel backend (§11), a config change (new device, `id_iot` edit, `read_from` switch, deactivation) reaches the subscription set on the very next refresh tick, not after a fixed TTL. On reconnect, the broker forgets all subscriptions — the full previously-known topic set is reasserted unconditionally before the next diff runs. **Gotcha:** since `id_iot` can itself contain `/` (as it does here), the subscribed topic can't be reversed back to an `id_iot` by splitting the incoming topic on `/` and indexing the placeholder's position — `MqttChannelSource` keeps an explicit `topic → id_iot` map built at subscribe time instead, and looks up incoming messages by the raw topic string, never by positional split.
- **Flat shared topic** (default, e.g. `machine/status`, no placeholder segment): subscribed literally — every device publishes to the exact same topic, so the match value is instead read from the JSON payload's field named by `MQTT_MATCH_FIELD` (`'ip'` default, or `'id_iot'`).

On each message, the parsed `{ inputs: boolean[], counts: number[], ... }` payload is cached keyed by whichever value was matched, with a timestamp — same grouping convention as API/MODBUS's `ip`-keying, just with `id_iot` as an alternative key. A missing/invalid `counts` array is tolerated (warned, defaults to 10 zeros); a missing `inputs` array rejects the message entirely (same as before). `getLatestForMachine(ip, idIot)` picks the right one of the two to look up based on this deployment's configured match field, and returns `null` (offline) if there's no cache entry or it's older than `MQTT_STALENESS_MS`, else a `ChannelAcquisition`. Reconnects rely on the `mqtt` package's built-in backoff. `MQTT_BROKER_URL` is normalized to prepend `mqtt://` if no protocol is given, and `connect()` is wrapped in try/catch — a bad broker URL disables MQTT with a logged error instead of crashing the process. A machine with no value in whichever field is configured as the match field is permanently treated as offline (same as API/MODBUS with no IP).

**Important:** `{ip}`-templated and flat-topic modes are a passive, broker-wide subscription — they receive and cache **every** message published to the subscribed topic shape, regardless of whether any machine's DB config actually references that device via `read_from='MQTT'`. A device broadcasting on the shared topic will show up in `CHANNEL_POLL_DEBUG_LOG` logs even if no machine is configured to read it — that's expected, not a misconfiguration, in those two modes. `{id_iot}`-templated mode is the opposite: it only ever subscribes to devices actually present in the DB with `read_from='MQTT'`, so an unconfigured device's messages are never received at all (broker permitting — see below), not just ignored downstream. In every mode, the thing to check when a device's data isn't being _used_ is that machine's `read_from` actually says `MQTT` (and, if keying by `id_iot`, that its `id_iot` column is set and matches the device's real topic) — a machine left on `MODBUS`/`API` while its hardware only speaks MQTT will spin on connection failures against a transport the device never listens on.

> **Source of truth:** channel→state mapping lives in `config_has_channels` (`config_id`, `channel_id`, `machine_state_id`), edited via the machine-config form — constrained server-side to states the machine is tagged with in `machine_has_states` (`MachineConfigController` validation), so a channel can't be wired to a state the machine was never configured to use. The old `status` ENUM column (`active`/`idle`/`maintenance`/`inactive`) still exists alongside `machine_state_id` for backward compat during the migration window (kept in best-effort sync — a legacy-named state writes both columns, a custom state only writes `machine_state_id`) and is scheduled for removal once the switch-over is fully verified in production (same treatment for `machine_state_events.state`). `read_from` on `machine_has_configs` selects the acquisition transport per machine; `ip_plc` is the shared grouping key for API/MODBUS (and MQTT, if keyed by `ip`); `id_iot` is the alternative grouping key for MQTT only. The legacy `machine_has_configs.gpio_status_map` JSON column was dropped.

**Choosing `read_from` — load profile, lightest to heaviest on the ESP32-P4 (`PROTOCOLS_DATA.md`):**

- **MQTT** — lightest. Push-based: the device publishes on its own timer over one already-open connection; node-server never sends it a request at all, just reads a cache (`MqttChannelSource`). Load on the ESP32 doesn't scale with node-server's poll cadence or fleet size — the broker absorbs fan-out. Best choice at scale (200+ machines) if a broker is already running reliably. A 1s publish interval is negligible for the device, the broker (msgs/sec is trivial for any real broker), and node-server (`handleMessage` is just `JSON.parse` + a `Map.set`, no DB/Redis write per message) — publish rate only affects cache freshness, not the `MQTT_STALENESS_MS` offline-detection window.
- **MODBUS** — moderate. Persistent binary connection (connect once, read-on-tick), no HTTP parsing/JSON overhead, but still request/response — the device answers a read every tick at whatever cadence its tier resolves to.
- **API/HTTP** — heaviest. Full HTTP request/response every tick (headers, JSON encode/decode, and — since `axios.get` here has no keep-alive agent configured — likely a fresh TCP handshake per poll). Most likely to strain a small MCU under load.

**Never mix `read_from` across machines sharing one `ip_plc`** — see Known issue #9 (§13): the poller has no cross-transport dedup, so a split-transport PLC gets hit concurrently by two different protocols every tick, which can crash/reset the device.

**State-change history (`machine_state_events`):** status is broadcast every tick, but **persisted only on a debounced/confirmed transition**. A per-machine `lastState` Map (keyed by `machine_id`) is the fast-path cache; when a machine's lowercased (debounced) state differs, it's added to that tick's `changed[]` batch. `ChannelMappingService.persistTransitions` calls the shared `MachineStateTrackerService.recordTransitions` **once per tick for the whole batch** — one `findMany` for every currently-open row across all changed machines, one raw bulk `UPDATE ... WHERE id IN (...)` (computing `duration_seconds` via `ROUND(TIMESTAMPDIFF(MICROSECOND,...)/1e6)` — rounds to the nearest second, matching the single-machine path's `Math.round`, not `TIMESTAMPDIFF(SECOND,...)`'s truncation, which would silently undercount by up to 1s per row), then one `createMany` for every new open row — instead of N individual find+transaction round trips for a mass event (e.g. shift start moving hundreds of machines to `ACTIVE` in one tick). The open-row check is read from the DB, so it is idempotent across restarts (no duplicate row for an unchanged state). A batch failure invalidates every entry's `lastState` cache so the whole batch retries next tick — never breaks polling. This history feeds runtime / idle / maintenance / OEE / KPI calculations (current state = `ended_at IS NULL`; per-state totals = `SUM(duration_seconds)`). PLC-offline resolves to `INACTIVE` and is recorded as a real transition (downtime).

**Debounce/OEE tradeoff, explicitly:** debouncing delays a genuine transition's registration by up to `CHANNEL_STATUS_DEBOUNCE_MS`, shifting that same amount onto the closing state's duration (inflated) and the new state's early duration (understated) — a small, bounded, predictable bias. The alternative (no debounce) is _not_ a more-accurate baseline: contact-bounce/electrical-noise flicker creates phantom transitions with **unbounded** error, fragmenting uptime data into garbage. Debounce trades that unbounded noise for a small known lag — the correct call for OEE, but real, and tunable via `CHANNEL_STATUS_DEBOUNCE_MS` if a tighter or looser window is needed.

**Also true for legacy worker mode:** `MachineRuntimeService` calls the shared `MachineStateTrackerService.recordTransition` (single-machine path, §10) — `machine_state_events` and `machine_status_runtime` are not channel-mapping-exclusive.

**Stale-entry pruning (`pruneStaleEntries`):** runs inside `watchTiers` every `CHANNEL_TIER_WATCH_MS`, using the freshly-loaded config to compute the currently-active machine-ID and PLC-IP sets. Anything in `lastState`/`statusDebounce` keyed by a machine ID no longer present, or `plcHealth`/`modbusConnections` keyed by a PLC IP no longer present, is dropped — `modbusConnections` entries are properly torn down (socket destroyed), not just deleted from the map. Also calls `machineGateway.forgetMachine(id)` to drop the machine from the gateway's own `machineState`/`plcState`/pending-broadcast maps. Without this, a system meant to run for months/years with machines being decommissioned/renumbered would accumulate stale map entries indefinitely.

## 16. Calculations module (`calculations.module.ts`) — read-heavy Angular aggregation endpoints

**Not part of the acquisition/runtime pipeline described in §1–§15.** This is a second, independent Nest module that happens to live in the same `src/module/machine/` directory because it reads the same tables (`machine_state_events`, `machine_production_counts`) the pipeline above writes. It exists purely to serve the Angular machine-overview page (`/production/mco`) — see the frontend's own docs, [`Frontend/docs/production-management/shared/MACHINE_OVERVIEW_DATA_SERVICE_CONTEXT.md`](../../../../../Frontend/docs/production-management/shared/MACHINE_OVERVIEW_DATA_SERVICE_CONTEXT.md) and [`Frontend/docs/production-management/work-order-and-log-production.md`](../../../../../Frontend/docs/production-management/work-order-and-log-production.md), for the consumer side.

**Why it lives in node-server at all, not Laravel:** these were originally Laravel endpoints (`MachineController::overview`/`stateSecondsInRange`, `WorkOrderController::detail`). They were moved here because node-server already owns the write side of `machine_state_events` (§9, §15) and `machine_production_counts` (worker-relayed `record_production_shot`, §9/§10) — the aggregation logic now lives next to the tables it reads instead of being duplicated across two backends. **Work-order CRUD and manual production-count logging stayed in Laravel** (`WorkOrderController::store/update`, `MachineController::assignedWorkOrders/logProductionCount`) — only read-heavy calculation moved.

**Wiring (`calculations.module.ts`):** imported directly in `AppModule`, deliberately **not** nested under this module's own `route.ts`/`RouterModule` tree (which already mounts `MachineModule` at `/api/machine`) — nesting would have doubled the prefix to `/api/machine/api/machine/...`. Each controller below carries its own full `@Controller('api/...')` path instead. Both routes are behind the same `AuthMiddleWare` as the rest of `/api/*` (wired in `AppModule.configure()`, not this module).

**`computeOee(machineWindowById, totalGood, totalCount)`** (private) — OEE scoped to this
one work order, not a machine or a date range. In the same loop that builds the
`(machine_id, shift_id)` rollup rows, `detail()` also builds a **per-machine-only** window
map (`machineWindowById`): each machine's overall engagement with this WO is approximated as
its earliest `bucket_started_at` → latest `bucket_ended_at` across every bucket logged
against it (regardless of shift) — buckets chain end-to-end per machine with no gaps, so
this window is a close approximation of "how long this machine spent on this job." One
`machine_state_events.findMany` (selecting `machine_state_id`, not the legacy `state` column)
fetches events for every involved machine over the union of
all windows (`machine_id: {in: [...]}`); each event is then clipped **in memory to its own
machine's window** (not the shared union range) before being summed into fleet-for-this-WO
`activeSeconds`/`totalSeconds` — `activeSeconds` sums whichever events' `machine_state_id` is
in the productive-id set (`loadProductiveStateIds()`, fetched once alongside the events via
`Promise.all`), not a hardcoded `state === 'active'` match — same clip-and-sum idiom used
everywhere else in this module, just windowed per machine instead of one shared range. Performance uses the
**average** `ideal_cycle_seconds` across the involved machines (same documented
approximation `ProductionDashboardService.fleetPerformance` uses, if that module is
present) weighted against the summed `totalCount`/`activeSeconds`. Quality is `totalGood /
totalCount` (passed in from `detail()`, not recomputed). All of `machine_state_events`,

work order (`machine_id: {in: machineIds}`), not the whole fleet.

### Known gaps

- Neither controller has its own automated test coverage — verified this session by seeding real rows via Prisma/tinker-equivalent and curling each route, then deleting the seed data (see the frontend's own doc for the verification steps taken).
- `shiftBreakdown` has no hard cap on requested range size — same gap as the frontend's own `MachineRuntimeHistoryService.getDailyBreakdown` (a multi-year range fetches/returns every day×shift row in that span, no pagination).
- Response shapes are deliberately snake_case, byte-identical to the Laravel endpoints they replaced, purely so `machine-overview-data.service.ts` on the frontend needed no mapping-code changes beyond the URL and the `isv8` routing flag — don't "clean up" the casing here without checking that consumer first.
